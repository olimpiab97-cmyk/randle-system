## 3. Prior blocker reconstruction

The blocked candidate used a measured worker but did not execute the governed controls. Its event loop emitted a predetermined conforming record for every expected policy identity; the enforcement stage echoed policy strings; observation construction produced matching values; the comparator produced no discrepancies from those constructed matches; and the external service signed the resulting internally consistent graph. The reported case-set identity did not resolve to immutable R7 case-definition bytes.

This proved that binary measurement, event cardinality, internal hash consistency, signature validity, and a durable append can all coexist with fabricated semantic provenance. The correction therefore requires corroborating request, response, process, caller/token, service, subject ledger, outer ledger, side-effect, observation, comparator, and trace evidence for every case.

## 8. Actual public-interface execution

Each run uses a fresh `RandleTerminalAuthorityR7SubjectLauncher.exe` process to start the pinned nonauthoritative execution subject. The service verifies the subject Git commit/tree and source blobs, measured launcher, Python binary and 3209-file runtime manifest, subject service/verifier/direct-interface files, and fixture helper before launch. The subject inherits the restricted service token; the signed suite process receipt records launcher and subject PIDs, parent, start/end/exit, command and environment identities, file identities, binary hashes, and SID/token evidence.

For each case the service creates canonical request bytes from immutable case data and a current one-shot case token, invokes the required public control, captures exact response bytes, and stores both content-addressed. It resolves subject execution and recorder records, inner subject ledger effects, outer ledger state before and after, and required or forbidden filesystem/process/IPC evidence. Physical-filename cases additionally require a newly created signed fixture-process receipt and exact reparse-point snapshot.

The pre-commit matrix executed 178 cases in each of eight runs, for 1424 real current-run case invocations.

## 9. Event derivation

`TerminalAuthorityR7Service_DRAFT.cs::BuildCurrentEvents` constructs one event only after a current invocation completes. The event binds run/case and immutable authority IDs, actual interface, suite and optional fixture process receipt, target process, request/response hashes and locators, outer and subject ledger evidence, observed effects and forbidden-effect checks, raw locators, constructor identity, schema, and governed timestamps. Its event root is calculated from canonical current event bytes.

The former predetermined event/enforcement methods are absent from service and worker source. An event cannot carry caller-authored conformity authority.

## 10. Observation derivation

The service launches a fresh measured worker in `derive-observations` mode. It receives the event-source locator, resolves fixed cases and raw current evidence, and derives actual outcome, code/classification, enforcing authority and function, interface invocation, process identity, ledger deltas, required effects, and forbidden-effect results. Every derived value cites current evidence. The worker input does not contain a desired final status.

## 11. Independent comparator

A second fresh measured worker runs `compare`. It independently resolves cases, expectations, events, observations, suite/fixture/observation process receipts, raw request and response bytes, subject and outer ledger evidence, and bidirectional trace. It verifies uniqueness and exact coverage, correct interface/caller/producer, current-run binding, expected semantics, required effects, and forbidden-effect absence. It emits an explicit row for each case and an explicit discrepancy list.

It rejects missing expectations or events, unresolved evidence, skipped/duplicate/extra cases, wrong interfaces/binaries/callers, fabricated or prior-run evidence, negative tests with forbidden effects, positive tests without required effects, and false traceability. A caller-supplied zero discrepancy count is not an input authority.

## 12. Terminal-verifier correction

The service `VerifyCurrentRunSemantics` stage re-resolves the entire graph before signing. It checks exact authority bytes, 178-case coverage, current run and process identity, request/response content, subject launch and ledger evidence, fixture evidence, observation citations, comparator inputs/rows/discrepancies, process index, service/worker/policy/trust/ledger identities, and trace in both directions.

Only after all checks pass does it reserve the terminal claim, sign and durably store the receipt, append the terminal commit, and persist the checkpoint. A valid signature over unresolved child data is rejected by the public verifier and cannot create terminal authority.

## 13. Reconciliation correction

Candidate and fresh receipts arise from distinct actual executions. A separate measured worker resolves both complete terminal graphs and outer ledger memberships, verifies both case/expectation authorities and all per-case/process/trace evidence, and proves required semantic equivalence alongside provenance disjointness. The service verifies the evaluator result and process receipt before it reserves, signs, stores, and commits the reconciliation receipt.

The four pre-commit pairs have distinct attempts, terminal run IDs and nonces, subject runs/processes, event roots, evidence/observation/comparator/process-index/trace locators, terminal receipts, reconciliation processes, and reconciliation receipts. Two internally matching synthetic receipts are rejected.
