# Independent Architecture Impact Assessment and Canonical Delta findings

## Required authority division

The governed architecture requires:

`runtime proposal → hostile-capable external governed execution → immutable current raw evidence → independent semantic comparison → isolated restricted-service full-graph proof → durable signed terminal receipt → public verification → full external reconciliation`.

The candidate instead implements:

`trusted same-SID service child → case-id-selected f0 fixture/meta handler conditioned by expected values → child-reported outcome and identities → copied observation/shared expectation comparison → structurally validating service sharing the child's key/store principal → signed ledger receipt → structural reconciliation`.

## AIA findings

- Runtime and worker are declared nonauthoritative but possess the service token, key use and authority-store modification rights; the declared division is false.
- The service alone is intended to issue terminality but cannot distinguish independently derived evidence from an expectation-conditioned hostile-child graph.
- Comparator executable separation is not semantic independence.
- Fixture/meta handlers replace real hostile external surfaces for all 158 negative cases.
- Reconciliation resolves substantial structure but can reconcile two graphs of the same invalid synthetic class.
- Recovery cannot reliably reconstruct a response or checkpoint state after the identified crash windows.
- The v3/DRAFT upgrade is outside the v1 provisioning attestation and lacks an authorized lifecycle.
- The 14,471-file host surface contains unbound Git and per-use Python dependencies, stale tools and one retained test junction.

## Canonical Delta findings

The implementation's proposal-only Canonical Delta overstates demonstrated closure for real execution, independent expectations/comparison, service semantic verification, trust continuity, public verification, replay/idempotency and reconciliation. No canonical incorporation is authorized by this review.

A future proposal must accurately classify at least these unresolved controls:

1. distinct child/service principals and key/store capabilities;
2. separately authorized service/policy/interface upgrade and anti-downgrade state;
3. direct derivation of events/observations from raw public-interface side effects;
4. independently authored expectation authority with no execution-input coupling;
5. strict framed canonical parser and runtime schema/semantic enforcement;
6. transactionally recoverable response/checkpoint/abort/supersession states;
7. graph-reachable governed subject/dependency authority;
8. version-aware public verification of all retained receipts;
9. complete real outer terminal/reconciliation cases and a newly authorized matrix;
10. corrected bidirectional traceability and evidence provenance.

All implementation artifacts remain DRAFT/proposal evidence. Acceptance, merge, canonical incorporation, deployment and trading authorization remain outside scope.
